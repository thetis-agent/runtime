# Plan: a data-driven web gateway skeleton, and the packages that extend it

**Date:** 2026-09-15. **Status:** implemented 2026-09-15, phases 0–5 (a project has zero or more project directories, none by default). **Scope:** `@thetis/gateway-web` and the packages that will
contribute UI to it. No kernel change until phase 5 (projects), and that one is a fence bind, not behavior.

Each phase leaves `npm test` green and production usable. Phases 0 and 1 are the skeleton. Everything after
is a package that plugs into it, in the order that proves each seam before the feature that needs it.

---

## 0. What exists, and what v2 already learned

`@thetis/gateway-web` today is one package that runs inside each person's fence as a service, serves a
page with no build step, and knows about every feature: the todo chip and card, the `ask_user` form, the
control panel and its five sections, the marketplace table. The browser side is ten views and eight lib
modules sharing one observable `store` (`assets/lib/store.js`); the server side is `server.ts` (sessions,
events, static files), `panel.ts` (packages, marketplace, admin) and `turns.ts`. Everything reads the
kernel by name through `KernelClient`; the page imports nothing from the server. That part is right and
stays.

What is wrong for iteration: adding a UI feature means editing `app.js`, `index.html`, `app.css` and a view
in `gateway-web`, and a tool package (`@thetis/tools-plan`) has its UI living in a different package than
its tool. The parity work of 2026-09-14 (`views/plan.js`, `views/ask.js`) was done by forking the whole
gateway. That is the cost this plan removes.

v2 solved this once (`/tank/data/Dev/thetis-agent.v2`: ADR 0038 and 0051; `packages/gateway-web/panels.ts`,
`assets/lib/surface.js`, `assets/views/rail.js`, `assets/views/stage.js`; the packages `inspector-tools`,
`inspector-context`, `tools-todo`, `tools-ask`, `tools-terminal`). The design canvas
(`design-canvas/`, generated by `build_*.py`) says the same in its annotations: "Tools and Skills should
ship as add-on packages rather than baked in", needing a panel contract and a panel host. The parts worth
carrying over, translated to this runtime's package model:

| v2 rule | Why it held | Here |
|---|---|---|
| A package declares its UI in its manifest (`surface` block), read once when the gateway composes | Reach is fixed at publication and reviewed with the code | `thetis.ui` in `package.json`; the kernel never reads it, exactly like `thetis.bench` |
| Discovery is a readdir of sibling packages, never a list in code | A new panel is an empty `git diff packages/gateway-web` | The gateway reads `thetis.ui` from `kernel.packages.list()` |
| A contributor's assets are served only under its own segment | No package serves over another | `/ext/<package>/…` from `<store>/node_modules/<package>/<ui.dir>/` |
| A malformed contributor is refused **by name and skipped**, never fatally | A missing tab beside a named refusal beats a dead page | `/api/ui` carries `refused: [{ package, message }]` |
| Panels never touch the socket; the only thing a panel may originate is a declared verb, checked on the host | A panel cannot invent traffic, outlive its conversation, or see more than the person | `ui.commands[{ verb, export, role? }]`; `POST /api/ext/<package>/<verb>` checked by the gateway |
| Several packages may draw one transcript row kind; each may decline; a broken one falls through | Two tool packages are not mutually exclusive | `ext.transcript(render)` with fall-through to the built-in row |
| Six defects passed every unit test and were found in an hour in a browser | Fixtures built to agree with the code | Phase 1 ends with a browser smoke test, not only node tests |

One thing v2 did that this plan does not: reading the calling module's package name out of a stack trace.
Here the shell imports each extension module and calls its `install(ext)` export with an `ext` object bound
to that package, so a panel cannot name another package because it never names one.

## 1. The shape

### 1.1 Layout, from the canvas

`Main.dc.html`: `.app` is a column of `.zones` (a row: sidebar, main, rail) over a full-width status bar.

```
| sidebar 272px | main: tabs / chat bar / transcript (measure 48rem) / composer | rail 44px | dock 0 · 360 · 620 (wide) |
| status bar 26px, full width, empty until a package fills it                                                             |
```

- **Sidebar** (left, `--sidebar-w: 272px`, no collapsed state in the design; the narrow-screen veil stays).
  Brand, **New chat**, one **head slot** (the project switcher in phase 5), search, the conversation list
  with Today/Yesterday/…/Archived, the footer with identity, connection state, and the **places**: today
  **Control panel** and **Log out**; **Marketplace** joins in phase 4.
- **Main.** A tab strip with **one tab per open conversation** (`.stage-tab`: title, a dot while a turn
  runs, a close ✕; a trailing `+`). Clicking a sidebar row activates or opens its tab. Under it the chat bar
  (title, state, pickers and chips, archive), the transcript, the composer. Switching tabs shows and hides
  panes and never rebuilds a transcript (v2's `stage.js` rule: a background conversation keeps receiving
  events).
- **Places.** The control panel is not a tab. It **takes over the main and rail region** with the sidebar
  kept, has a header ✕ and Escape to return, and is entered from the sidebar's ≡ menu (footer links until 2026-09-15). The skeleton makes
  that a general mechanism: a *place* is any non-conversation surface a package registers, drawn in the same
  region the same way. The control panel is the first place; the marketplace, a package's page, and a
  project's settings are places too.
- **Rail** (the vertical navbar, 44px, 32×32 buttons with a tooltip): one entry per registered **dock
  panel**, in declaration order. The canvas order is Context (wide), Skills, Tools (wide), Todo, Models,
  People, Environment; Branch and Files are deliberately out. Clicking opens the dock on that panel; the
  active one again, the header ✕, or Escape closes it.
- **Dock** (the right sidebar): hidden when nothing is selected; 360px, or 620px for `wide`. A header
  (title, subtitle, actions, ✕) and a body the panel draws. "Never modal; the chat reflows beside it."
- **Shelf** (the bottom dock): the terminal's home in the canvas (`Terminal.dc.html`): 360px tall,
  resizable by a grip, sits *under* the conversation and shortens it, with a vertical list of terminals at
  its right (190px). The skeleton reserves the slot and draws nothing until a package registers.
- **Chat bar chips** are shortcuts into the matching surface (`todo 4/7` opens the Todo dock, `2 shells` the
  shelf, `$0.42` the Context dock's Usage tab). **Composer pickers** (mode "Plan", the model, later an agent)
  are a slot too; the model picker is built in, the mode picker comes with a package.
- **Status bar**: left a working dot, then facts (setup, environment, memory, load), right the version. All
  of it is contributed; the skeleton draws the bar only when something registers.

### 1.2 The manifest field

```json
"thetis": {
  "type": "tool",
  "tools": [ … ],
  "ui": {
    "dir": "ui",
    "entry": "index.js",
    "style": "index.css",
    "dock":     [ { "id": "todo", "label": "Todo", "icon": "M5.5 3.5h9v13h-9z …", "hint": "The plan the agent is working to", "wide": false } ],
    "panel":    [ { "id": "people", "label": "People", "note": "Who can sign in.", "role": "admin" } ],
    "places":   [ { "id": "marketplace", "label": "Marketplace", "icon": "…" } ],
    "sidebar":  [ { "slot": "head" } ],
    "chips":    [ { "id": "todo" } ],
    "composer": [ { "id": "mode" } ],
    "shelf":    [ { "id": "terminal", "label": "Terminals" } ],
    "statusbar":[ { "id": "load", "order": 40 } ],
    "commands": [ { "verb": "plan", "export": "uiPlan", "label": "Read the plan", "role": "user" } ]
  }
}
```

| Key | Meaning |
|---|---|
| `dir` | The directory of browser assets, relative to the package root. Served at `/<user>/ext/<package>/…`. Only `.js`, `.css`, `.svg`, `.json`, `.md`. |
| `entry` | The ES module the shell imports after the page has mounted. Optional: a package with only a stylesheet or only static declarations needs none. |
| `style` | A stylesheet the shell links once. Optional. |
| `dock`, `panel`, `places`, `sidebar`, `chips`, `composer`, `shelf`, `statusbar` | Static slot declarations. The shell draws the rail icon, the panel nav item, the sidebar place, the placeholder from these **before** the module loads, so the layout is settled by data, and a module that fails to load leaves a named gap, not a missing button. |
| `commands` | The verbs the package's own UI may send to the package. `export` names a function in the package's `main`. `role` is the least role that may send it; default any signed-in person. |

Types go in `@thetis/contracts` (`UiDecl` on `ThetisField.ui?`). No kernel code reads it; `validateManifest`
does not reject unknown fields, so the field reaches the gateway through `PackageInfo.thetis` untouched.
The gateway validates it and refuses by name.

### 1.3 Server routes added to the gateway

| Route | Effect |
|---|---|
| `GET /api/ui` | `{ extensions: [{ package, version, entry?, style?, dock, panel, places, sidebar, chips, composer, shelf, statusbar, commands: [verb…] }], refused: [{ package, message }] }`. Composed on each request from `kernel.packages.list()`; installs are rare and the list is small. Command exports and roles stay server-side; the browser gets verbs only. Panel entries above the person's role are dropped, as sections are today. |
| `GET /ext/<package>/<path>` | A static file from `<store>/node_modules/<package>/<dir>/<path>`. `404` unless the package is installed here, declares `ui`, and the resolved path stays inside `dir`. Same content types as `/assets`. |
| `POST /api/ext/<package>/<verb>` | Body `{ session?, args }`. Checks, in order: the package is installed and declares the verb; the person's role clears the declared role; `session`, when given, is one of the person's own (`kernel.sessions.inspect`). Then imports the package's `main` from the store and calls `export(args, env)` where `env` is the `StepEnv` the gateway already holds plus `{ session, user }`. Result: `{ text?, data? }`, JSON-encoded, capped at 256 KiB. A thrown error answers `400 { error }` with the message; a timeout (30 s) answers `504`. |

The command path is the one place the gateway runs another package's code. It runs in the same fence,
as the same person, with the same authority the package's tools already have when the model calls them.
What the handler does **not** get is `config.packages[<name>]`: the kernel sends a package's configuration
only into that package's steps and tools. Handlers that need it read their own files instead. Written down
so nobody looks for it.

### 1.4 The browser seam: `assets/lib/ext.js`

The one module an extension may use, handed to it as the `ext` argument of `install(ext)`:

```js
export default function install(ext) {
  ext.dock("todo", { draw: () => ({ title, subtitle, body, actions }) });     // matches ui.dock[].id
  ext.panel("people", { mount: (root, { role, user }) => unmount });           // matches ui.panel[].id
  ext.place("marketplace", { open: (root, params) => unmount });               // matches ui.places[].id
  ext.sidebar("head", (root) => unmount);                                      // matches ui.sidebar[].slot
  ext.chip("todo", { draw: (button) => void, open: () => void });             // matches ui.chips[].id
  ext.composer("mode", { mount: (root) => unmount });                          // matches ui.composer[].id
  ext.shelf("terminal", { mount: (root) => unmount });                         // matches ui.shelf[].id
  ext.statusbar("load", { draw: (node) => void });                             // matches ui.statusbar[].id
  ext.transcript((event, ctx) => node | null);                                 // tool rows; null declines
  ext.request("plan", { session, args })  -> Promise<{ text, data }>;          // POST /api/ext/<own>/<verb>
  ext.events.watch((message) => void);                                         // every turn message, every session
  ext.conversation: { current, watch(fn), send(text), open(id) };
  ext.sessions: { list(), watch(fn), filter(fn) };
  ext.open: { dock(id), place(id, params), shelf(id) };                        // the chips' shortcuts
  ext.dom: { el, icon, clear, setHidden };  ext.ui: { table, badge, button, field, kv, card, confirm, busy, pill, section };
  ext.toast;  ext.markdown;
}
```

Rules the seam enforces: a registration whose id is not in the package's declaration is refused with a
console message; a `draw`, `mount`, `open` or `render` that throws is caught and reported once, and the
slot shows "`<package>` could not draw this"; a transcript renderer that returns nothing falls through to
the next, then to the built-in row. Extensions never see `store`, `api`, `connect`, or `views/*`.
`ext.conversation.send` exists because an `ask_user` form's answers must travel the composer's own path
(`app.js` today: "the pending row and failure handling apply for free").

## 2. Phases

### Phase 0 — Restructure without changing behavior

Goal: the same page, same tests, new internal shape. No new feature. The phase to do carefully and boringly.

1. **Layout.** `index.html` gains the tab strip (`#tabs`), the pane host (`#panes`), the place host
   (`#place`), the rail (`#rail`), the dock (`#dock`), the shelf (`#shelf`), the status bar (`#statusbar`)
   and the sidebar slots (`#sidebar-head`, `#sidebar-places`). `app.css` becomes the grid of 1.1 with the
   canvas widths. Everything new is `hidden` or empty, so nothing visible changes.
2. **Tabs and places.** `views/tabs.js`: one pane per open conversation, `+`, close, activate; the sidebar
   opens or activates. `views/places.js`: `open(id, params)` swaps the main and rail region for the place
   and `close()` restores it. The control panel becomes the first place; the `is-panel` class and the
   takeover code in `views/panel.js` go.
3. **Registry.** `lib/registry.js`: the slot tables (`dock`, `panel`, `places`, `sidebar`, `chips`,
   `composer`, `shelf`, `statusbar`, `transcript`) with the fall-through and the once-only error reporting.
   The built-in pieces register through it: the Packages section as a `panel` entry, the control panel as a
   `places` entry, the todo chip as a `chips` entry, the ask form and the plan lines as `transcript`
   renderers, the model picker as a `composer` entry. `app.js` shrinks to wiring.
4. **Server.** `src/ui.ts`: `composeUi(packages, role) → { extensions, refused }`, the `thetis.ui`
   validator, `serveExt`, `runCommand`. `server.ts` mounts the three routes of 1.3. `src/panel.ts` untouched.
5. **Seam.** `lib/ext.js` with the API of 1.4, and `lib/loader.js`: fetch `/api/ui`, draw the static slots,
   link each `style`, `import()` each `entry` and call `install(ext)`; a failure is one toast per package
   and a named gap.
6. **Contracts.** `UiDecl` in `packages/contracts/src/packages.ts`; `ThetisField.ui?`.

Tests (node, in `test/gateway.test.ts` and a new `test/ui.test.ts`):
- a fixture package under `packages/host/test/fixtures` with a `thetis.ui` block, a `ui/index.js`, a
  `ui/index.css` and one command export;
- `/api/ui` lists it after install and drops it after uninstall; a fixture with a bad declaration (an
  entry outside `dir`, a command with no export, a duplicate dock id) appears in `refused` by name and
  the good one still composes; an admin-only panel entry is absent for a user;
- `/ext/<pkg>/index.js` serves; `/ext/<pkg>/../package.json` is `404`; `/ext/<other-installed-pkg>/x` is
  `404` when that package declares no `ui`;
- `/api/ext/<pkg>/<verb>`: `404` for an undeclared verb, `403` below the declared role, `404` for a
  session of another person, `200 { text, data }` otherwise, and the handler saw `session` and `user`;
- everything that passes today still passes.

Done when: `npm test` is green, `git diff --stat` shows `index.html`, `app.css`, `app.js` and the new
modules, and a manual pass on `.devhome` finds the page as it was, plus conversation tabs.

### Phase 1 — Prove the dock with a reader, then test in a browser

Goal: the first extension package, chosen because it needs no new data: **`@thetis/ui-tools`**, the Tools
inspector of `Tools.dc.html`. It draws, for the open conversation, every tool the installed packages
declare, one section per package (`tools-files@1.0.0 · 7`), cards with the name, description, parameters
and a badge (`reads only` / `changes files`), and a "Turned off right now" section that stays empty until
projects or a mode package withhold tools. It gets the list through `ext.request("tools")`, whose export
returns `env.kernel.packages.list()` reduced to names and declarations. One dock entry (`wide`), one
command, one module, one stylesheet. Installed for everyone in `systemPackages["*"]`.

Then the browser check. There is none today, and v2's parity report is explicit that the defects worth
finding are the ones node tests cannot. Decided 2026-09-15: **no Playwright dependency in the repo.** The
check is driven through the Playwright MCP browser against a `.devhome` gateway (`docs/15-web-gateway.md`
§10), following a written checklist in `packages/gateway-web/test/BROWSER.md`: sign in, open a
conversation, send one message through the echo provider, open the Tools dock from the rail, close it with
Escape, open a second tab, open the control panel place and return. Each step names the DOM it expects
(a transcript row, the tab, the rail button, the dock title). The checklist is run, and its result written
into the phase's commit message, before any phase is called done.

Done when: the dock opens and closes from the rail and Escape, a second dock package (a two-line fixture)
appears beside it in declaration order, and the checklist passes.

### Phase 2 — A tool package carries its own UI: `@thetis/tools-plan`

Goal: the todo plan and `ask_user` leave the gateway. `tools-plan` gains `ui/` with:

- `dock: [{ id: "todo", … }]`, the Todo pane of `Todo.dc.html`: "4 of 7 done", one row per item with the
  ✓ ● ○ glyph, text, note, and the mono id; a person can tick a row through `commands: [{ verb: "mark" }]`
  (v2's rule: the row is disabled until the package answers, because the answer is the plan);
- `chips: [{ id: "todo" }]`: the `todo 4/7` chip in the chat bar, opening the dock (`ext.open.dock`)
  instead of today's popover;
- `transcript` renderers for `todo_*` (one quiet line) and `ask_user` (the form of `Transcript.dc.html`:
  "Thetis needs a decision", options, Skip, Answer). Submit calls `ext.conversation.send(text)`;
- `commands: [{ verb: "plan", export: "uiPlan" }, { verb: "mark", export: "uiMark" }]`, thin wrappers over
  `lib/plan.js`, which already reads and writes `plans/<session>.json`.

`views/plan.js` and `views/ask.js` are deleted from the gateway. The `todoArgs` map and the `isTodoTool`
branches in `transcript.js` go with them; what remains is the generic tool card and the renderer hook.

This is the phase that answers "a todo package includes the tools definition and optionally loads the UI
elements IF the gateway ui package is installed": `thetis.ui` is inert data until a gateway that reads it
is present. The CLI gateway ignores it. A person who forks `tools-plan` gets its UI with the fork.

Tests: the plan and ask node tests stay; the browser test gains "a message that triggers `ask_user` in the
echo fixture draws the form; answering it sends the next user message".

### Phase 3 — The control panel as a slot: `@thetis/ui-admin`

Goal: People, Models, Activity, Overview move to one admin package with `panel: [{ id, role: "admin" }]`
entries and commands that call `env.kernel.operator.call(...)` (allowed by the kernel only when the fence's
user is an admin; the gateway checks the declared role first, so the three checks of `17-control-panel.md`
§2 hold as they do today). `/api/admin/*` and the four `panel-*.js` views leave the gateway. The Packages
section stays built in.

This proves the panel slot and role-gated commands with code that already has tests. From then on an
option in the panel is a package with one `panel` entry. The canvas's twelve-item nav (Overview, Updates,
Conversations, Accounts, Models & providers, Modes & agent, Limits & budgets, Skills & tools, Packages,
Secrets, Registries, Build & recovery) is what packages fill in over time; its per-package settings rows
(`retriever-local.fusionWeight`, `gateway-web.streams`) need a way to write `config.packages[<name>]`,
which the kernel does not offer today (`config.get` only). That is a later operator method, not part of
this plan.

Also here, small and independent: `harness-core` gains an `after` step that writes
`harness["@thetis/harness-core"].lastCall = { system, tools: names, messages: count, model }`. That is
the data the **Context** inspector of `Context.dc.html` (`@thetis/ui-context`: Request / Prompt / Usage
tabs, the budget bar, the message list with token counts) needs, and nothing on the event stream carries
it. No kernel change: `harness` is a package's variable. The **Skills** pane (Always included / Retrieved
/ Dropped for budget, with scores) waits for skills (`13-limitations-and-roadmap.md` §3 item 6); when skill
packages exist their pane ships with them under the same field. **People** in the rail is a multi-person
conversation, which ADR 0052 refused; not planned. **Environment** and the status bar's facts belong to
`ui-admin` when there is something to show.

### Phase 4 — The marketplace as a place: `@thetis/ui-marketplace`

Goal: the marketplace leaves the control panel and becomes a top-level place with package pages, closer
to the VS Code marketplace than the canvas's detail column.

- `places: [{ id: "marketplace", label: "Marketplace" }]` adds **Marketplace** beside **Control panel** in
  the sidebar footer. Both open in the main and rail region with the sidebar kept, as the canvas draws the
  panel. (A rail entry was considered and dropped: the rail is for panels *about the open conversation*.
  A mode switch on the sidebar list was considered and dropped: it hides the conversations to show
  packages. The footer is where the canvas already puts the door to the panel.)
- The place has two views with browser history between them: the **gallery** (search, type filter, cards
  with name, description, version, registry, and the badges Installed / Only me / Everyone / Available /
  update to *v*), and one **package page**: the README rendered with `ext.markdown`, the tools and steps it
  brings with their descriptions, versions (the pin installed here against the registry's tip), and the
  actions the person's role allows: Install, Install for everyone, Update, Remove, Make it the default for
  everyone. The confirm popovers stay, with the facts they state today.
- Commands: `search`, `show`, `install`, `installEveryone`, `update`, `remove`, `promote`, over the index in
  `env.shared` and `env.kernel.packages` / `operator`. The gateway's `/api/marketplace` route and its
  `@thetis/marketplace` import are deleted; the package imports `readIndex` and `search` itself.
- `@thetis/marketplace` (the service) copies each package's `README.md`, when one exists, to
  `<shared>/marketplace/readme/<registry>/<dir>.md` during a refresh, capped at 256 KiB, and the index
  entry gains `readme: true`. The mirror clone lives in the system userspace home, which no other fence
  can read, so the README must cross through the shared directory like the index does. A `screenshots/`
  directory can follow the same path later; it is not in this plan.

The control panel's Packages section shrinks to what is installed here, each row linking to its page.

### Phase 5 — Projects: `@thetis/projects`

Goal: named workspaces in the sense of Claude Code's projects: zero or more **project directories**
(mounted folders, which may sit outside the fence; default none), a per-project set of enabled and disabled
tools and skills, and standing instructions.

**The one change below the packages.** A project directory outside the userspace has to be bound into the
fence, and only the kernel may decide that. The mechanism is one bind in `packages/sandbox/src/bwrap.ts`; the
authority is a per-user mount list the host reads when it opens a fence:

```json
"mounts": { "alice": [ { "path": "/srv/repos/thetis", "mode": "rw" } ] }
```

- Decided 2026-09-15: a mount is bound **at its host path**, so `/srv/repos/thetis` is
  `/srv/repos/thetis` inside the fence too. Paths in `exec` output, git remotes, build tools and the
  person's own head all agree, and a project is named by the path the person already knows. (Binding
  under `home/projects/<name>` was considered because it left `tools-files` untouched; that saving is
  about fifteen lines and not worth a second path for everything.)
- The fence tells package code what is mounted: the agent's environment gains `THETIS_MOUNTS`, a JSON
  list of `{ path, mode }`, beside `THETIS_SHARED` (`03-fence.md` §3.5). `tools-files` reads it once and
  adds each mount to its roots (`rw` or `ro`), so `read_path /srv/repos/thetis/README.md` passes the
  containment check and a refusal names the mounts among the spaces you can reach. Absolute paths under a
  mount come back absolute, as they do for the shared directory today.
- Set by an admin: `thetis mounts add <user> <path> [--ro]` and the matching operator method
  `mounts.set`, stored in `$THETIS_HOME/mounts.json` (the kernel never writes the config file). A change
  applies when the fence next opens; `mounts.set` closes the person's fence, so their services restart and
  the mount is there within a second. Journaled.
- `Fence.open(userspace, rpc)` keeps its signature; the host passes the mounts through the `Userspace` it
  already builds (`Userspace.mounts?: Mount[]`, contracts). `ProcessFence` adds `--bind` or `--ro-bind` per
  mount after the userspace root bind and sets the variable. Kernel cost: about twenty counted lines.

**The package.** `@thetis/projects` is a `loader` with a `ui`:

- Data: `projects/<id>.json` in the home: `{ id, name, directories: [], tools: { enable?, disable? },
  skills: {…}, packages: { disable? } }`, and `PROJECT.md` beside it. `directories` lists host paths; it is
  empty by default, and a project with none is just a name, a tool set, and instructions; `projects/sessions.json` maps session id to
  project id. All written by the package's own commands; the gateway writes nothing.

### 6.2 Gateway routes (`src/ui.ts`, mounted in `src/server.ts` before the panel routes)

`GET api/ui` →

```json
{
  "extensions": [
    {
      "package": "@thetis/tools-plan", "version": "0.3.0",
      "base": "ext/@thetis/tools-plan/",
      "entry": "index.js", "style": "index.css",
      "dock": [ { "id": "todo", "label": "Todo", "icon": "…", "order": 100 } ],
      "panel": [], "places": [], "sidebar": [], "chips": [ { "id": "todo" } ], "composer": [], "shelf": [], "statusbar": [],
      "commands": [ "plan", "mark" ]
    }
  ],
  "refused": [ { "package": "@alice/broken", "message": "dock entry \"todo\" is already claimed by @thetis/tools-plan" } ]
}
```

Rules of `composeUi(packages: PackageInfo[], role: UserRole)`:
- a package without `thetis.ui` is skipped silently; one with it is validated: `dir` must not leave the package root; `entry` and `style` must resolve inside `dir` and exist; every entry `id` matches `^[a-z][a-z0-9_-]{0,31}$`; `commands[].export` must be a string; a verb declared twice is refused; a dock, place, chip, shelf, sidebar or statusbar `id` already claimed by an earlier package is refused **for that package**, by name (first installed wins). Panel ids are namespaced by package on the browser side (`<package>#<id>`), so two packages may both declare `people`; the shell shows both.
- entries whose `role` is above the person's role are dropped from the response; commands are listed by verb only.
- refusals are `{ package, message }`, one per package, and the rest still composes.

`GET ext/<scope>/<name>/<path…>` → the file at `<store>/node_modules/<scope>/<name>/<dir>/<path>` when the package is installed here and declares `ui`; `404` otherwise, for a path that leaves `dir`, and for an extension not in the `TYPES` table (`.js .css .svg .json .md`). `Cache-Control: no-cache`. The store is `env.store`; for an in-process gateway (tests) `GatewayOptions.store` overrides it.

`POST api/ext/<scope>/<name>/<verb>` with body `{ session?: string, args?: object }` →
1. `404` unless the package is installed here and declares the verb.
2. `403` when the person's role is below the command's role.
3. `404` when `session` is given and `kernel.sessions.inspect(session)` throws.
4. Import the package's `main` (`pathToFileURL(<store>/node_modules/<pkg>/<main>)` with `?v=<mtime>` like the agent), take the export; `500 { error }` if it is not a function.
5. Call it with `(args ?? {}, { ...env, user, role, session })` under a 30 000 ms timeout → `504 { error: "…did not answer in time" }`.
6. A string result becomes `{ text }`; `void` becomes `{}`; an object is passed as `{ text?, data? }`. Serialized JSON over 262 144 bytes → `502 { error }`. A thrown error → `400 { error: message }`.

### 6.3 The browser seam (`assets/lib/ext.js`) and the registry (`assets/lib/registry.js`)

The loader (`assets/lib/loader.js`) runs after the built-in views mount: `GET api/ui`, then for each extension in order: draw its static entries into the slots (rail button, panel nav item, place link, chip button, statusbar item) so they exist before the module loads; append `<link rel="stylesheet" href="<base><style>">` when given; `import(new URL("<base><entry>", document.baseURI))` and call `default(ext)` where `ext = createExt(extension)`. A failed import or a throwing `install` toasts once (`"<package> could not load its UI"`) and leaves the static entries drawn with a "could not load" tooltip.

`createExt(extension)` returns an object frozen against reassignment:

```js
ext.package                                    // "@thetis/tools-plan"
ext.dock(id, { draw })                         // draw() -> { title, subtitle?, body: Node, actions?: Node[] }; called on open and on ext.redraw(); id must be declared
ext.panel(id, { mount })                       // mount(root, { role, user }) -> unmount?; the control panel section
ext.place(id, { open })                        // open(root, params) -> unmount?; the header (title from the declaration, ✕) is the shell's
ext.sidebar("head", mount)                     // mount(root) -> unmount?
ext.chip(id, { draw, open })                   // draw(button) sets text/classes/hidden; open() runs on click
ext.composer(id, { mount })                    // mount(root) -> unmount?; root sits beside the model picker
ext.shelf(id, { mount })                       // mount(root) -> unmount?; the shell owns the grip and the close
ext.statusbar(id, { draw })                    // draw(node)
ext.transcript(render)                         // render(event, ctx) -> Node | null | undefined; ctx = { session, el, icon, markdown, restored: boolean }
ext.request(verb, { session, args })           // -> Promise<{ text, data }>; rejects with an Error whose message is the server's sentence
ext.redraw(id?)                                // redraws this package's open dock/chips/statusbar entries
ext.events.watch(fn)                           // fn({ session, turn, seq, event, input? }) for every turn message; returns unwatch
ext.conversation                               // { get current(), watch(fn), send(text) -> Promise, open(id) }
ext.sessions                                   // { list() -> SessionSummary[], watch(fn), filter(fn | null) }  filter narrows the sidebar; null clears
ext.open                                       // { dock(id), place(id, params), shelf(id), panel(id) }
ext.dom, ext.ui, ext.toast, ext.markdown       // { el, icon, clear, setHidden }, panel-ui exports, toast(text, opts), renderMarkdown(text) -> Node
```

Slot ids are `<package>#<id>` inside the registry. Built-in pieces register under the package `@thetis/gateway-web`. A registration whose id is not in the package's declaration logs and returns. A throwing `draw`/`mount`/`open`/`render` is caught, reported once per package per slot, and the slot shows `<package> could not draw this`. A transcript renderer that returns nothing falls through to the next registered one, then to the built-in row.
